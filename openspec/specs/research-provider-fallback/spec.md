# research-provider-fallback Specification

## Purpose

Keeps brief generation working through a primary research provider outage or quota exhaustion by automatically retrying the same request through a second, independently-provisioned provider, and tells the user which provider actually produced their brief.

## Requirements

### Requirement: Automatic retry on infrastructure-class failure

The system SHALL automatically retry a failed research-provider call through the fallback provider when the failure is infrastructure-class (rate limited, provider error, provider not configured, or a malformed/unparseable provider response), without the user needing to retry manually.

#### Scenario: Primary provider is rate limited
- **WHEN** the primary provider's call fails because it is rate limited
- **THEN** the system retries the same request through the fallback provider and returns the resulting brief if that retry succeeds

#### Scenario: Primary provider is unreachable or errors
- **WHEN** the primary provider's call fails with a transport or provider-side error
- **THEN** the system retries the same request through the fallback provider

#### Scenario: Primary provider returns an unparseable response
- **WHEN** the primary provider's response does not match the expected brief structure
- **THEN** the system retries the same request through the fallback provider

### Requirement: Content-class outcomes are never retried

The system SHALL NOT retry through the fallback provider when the primary provider's outcome is content-class rather than infrastructure-class: invalid input, no results found for the company, or an ambiguous company name.

#### Scenario: Company name matches no usable results
- **WHEN** the primary provider completes its search and finds nothing usable about the company
- **THEN** the system reports no results found and does not attempt the fallback provider

#### Scenario: Company name is ambiguous
- **WHEN** the primary provider finds the name matches more than one distinct company
- **THEN** the system reports the ambiguity and does not attempt the fallback provider

### Requirement: Fallback failure is reported like any other failure

The system SHALL report a failure to the user, using the existing failure-reporting behavior, when both the primary and fallback providers fail for the same request.

#### Scenario: Both providers fail
- **WHEN** the primary provider's call fails with an infrastructure-class error and the subsequent fallback attempt also fails
- **THEN** the system reports that research could not be completed, the same way it would if there were only one provider

### Requirement: Fallback is optional, shared infrastructure

The system SHALL treat the fallback provider as optional: when it is not configured, a primary-provider failure is reported exactly as it would be with no fallback feature present at all. The fallback SHALL be a single, app-provisioned resource shared by every account, not something an individual non-admin account must separately configure alongside their own research-provider credential.

#### Scenario: Fallback is not configured
- **WHEN** the fallback provider's configuration is absent and the primary provider fails with an infrastructure-class error
- **THEN** the system reports the failure without attempting a fallback call

#### Scenario: A non-admin account's request falls back
- **WHEN** a non-admin account's own research-provider call fails with an infrastructure-class error and the fallback is configured
- **THEN** the system retries via the fallback using the app's own shared fallback credentials, not anything the non-admin account supplied

### Requirement: Generated brief shows which provider produced it

The system SHALL record which provider produced a generated brief and SHALL display that to the user as part of the brief.

#### Scenario: Brief produced by the primary provider
- **WHEN** a brief is generated without needing the fallback
- **THEN** the brief indicates it was generated by the primary provider

#### Scenario: Brief produced by the fallback provider
- **WHEN** a brief is generated after the primary provider failed and the fallback succeeded
- **THEN** the brief indicates it was generated by the fallback provider, distinguishably from the primary-provider case
